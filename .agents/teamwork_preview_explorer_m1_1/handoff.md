## 2. Logic Chain
1. **Observation**: R1 and `PROJECT.md` require background delivery setup for 4 metric types (`.heartRateVariabilitySDNN`, `.restingHeartRate`, `.sleepAnalysis`, `.activeEnergyBurned`) with `.immediate` frequency.
2. **Logic Step 1**: Adding `startObservingBackgroundUpdates() async` will loop through `sampleTypesToObserve`, call `try await healthStore.enableBackgroundDelivery(for: sampleType, frequency: .immediate)` inside a `do-catch` block, instantiate an `HKObserverQuery`, and store active queries in `activeObserverQueries: [HKObserverQuery]`.
3. **Logic Step 2**: HealthKit background queries call update handlers on background queues. Since `HealthKitManager` is `@MainActor`, updating `@MainActor` isolated state requires hopping threads via `Task { @MainActor [weak self] in ... }`.
4. **Logic Step 3**: To avoid background processing suspension or process termination by iOS, `completionHandler()` must be called deterministically inside every exit path of the observer update closure.
5. **Logic Step 4**: Multiple observers can trigger simultaneously when Apple Watch updates metrics. Implementing `activeFetchTask: Task<Void, Never>?` in `fetchAllMetrics()` coalesces duplicate requests into a single 90-day data fetch operation.
6. **Logic Step 5**: Exposing `public var onDataUpdated: (@MainActor () async -> Void)?` enables downstream view models (`AppViewModel` in M2) to reactively recalculate readiness whenever background delivery fetches fresh samples.

## 3. Caveats
